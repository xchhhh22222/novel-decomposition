# 人物功能专项 QA 与跨书比较规则

## 1. 适用范围与权威关系

本文件只定义 `novel-character-function-miner` 的质量检查、重复疲劳检查和跨书比较规则，不新增或修改 `schema.md` 字段，也不替代总控的统一 envelope、证据优先级、状态约束和阶段门。

所有判断必须同时遵守：

- `skills/novel-dna-orchestrator/SKILL.md`；
- `skills/novel-dna-orchestrator/references/horizontal-specialist-contract.md`；
- `skills/novel-dna-orchestrator/references/integration-and-qa.md`；
- `skills/novel-character-function-miner/SKILL.md`；
- `skills/novel-character-function-miner/references/schema.md`。

QA 的目标不是给人物排名，也不是把人物标签做得更丰富，而是确认：

1. 人物功能来自可追溯行为和后果，而不是身份、性格、实力或出场频率；
2. 一个人的多个功能被分别取证，并能解释它们如何组合；
3. 关系发动机能说明关系为什么会持续制造剧情；
4. 功能阶段变化有 `before → trigger → after → evidence` 链条；
5. 替代性和不可替代性有具体依据；
6. 跨书比较的是功能运行方式，而不是“导师、妹妹、队友、反派”等表面称谓；
7. 所有结论仍是 `candidate`，不写正式人物库或素材库。

## 2. QA 结果与证据分级

### 2.1 单项结果

每项 QA 使用以下结果：

- `PASS`：证据充分，边界清楚，可以作为当前范围内的 candidate 继续流转；
- `HOLD`：已有部分证据，但存在关键缺口、争议或相邻专项边界不清，必须保留 `UNKNOWN`、`partial` 或 `gap`；
- `FAIL`：存在身份/性格替代功能、无证据功能、伪造关系发动机、阶段门违规、跨专项越界或其它结构性错误。

`HOLD` 不等于否定人物存在，只表示当前证据不足以支撑更强的功能结论。`FAIL` 不得进入高置信近邻或聚类。

### 2.2 置信度规则

- `HIGH`：核心功能、关系发动机、关键转变或替代性判断都有直接章节/阶段证据，且没有会改变结论的关键 `UNKNOWN`；
- `MEDIUM`：核心链条可追溯，但存在局部缺口、阶段范围不完整或需要人工确认的边界；
- `LOW`：只能确认人物出现、局部互动或一次性事件，无法确认稳定功能或持续关系发动机。

以下情况不得使用 `HIGH`：

- 功能主要来自身份、职业、性格、实力、称谓、立绘、标签、名字或简介；
- `actual_operation`、`target` 或 `evidence_refs` 缺失；
- 关系只有一次帮助、争吵、救援、赠送、误会或同框；
- `sustaining_condition` 或 `recurring_plot_generation` 缺失；
- `before_function`、`trigger_event`、`after_function` 中任一环节没有证据；
- `replaceable`、`identity_bound` 或 `non_replaceable` 只有主观评价，没有替代条件或绑定依据；
- 相邻专项结论没有被压缩成 interface/evidence reference；
- 全批次目标书未完成单书 QA，却已经生成跨书结论。

## 3. 第一层：单书人物功能 QA

### 3.1 输入范围与来源冻结

开始单书 QA 前必须确认：

- 目标 `book_id` 已由 orchestrator 冻结；
- 章节或阶段范围已冻结，覆盖分母明确；
- 允许读取的章节事实、阶段资料、情绪 overlay 和交叉索引已登记；
- 没有把书名、简介、人物目录或模型记忆当作未声明的证据源；
- 已知缺口和禁止输出已记录；
- 多书批处理的书籍或分片互不重叠。

输入范围不通过时，单书结果进入 `HOLD` 或 `gap`，不能继续生成高置信功能、近邻或聚类。

### 3.2 identity facts 可追溯性

逐条检查 `identity_facts`：

- 是否能回到公开身份、阵营、特殊身份或与主角定位关系的实际证据；
- 是否把职业、头衔、亲属、实力或性格误写成已证实的剧情功能；
- 是否把不确定的真实身份保留为 `UNKNOWN`，而不是用简介或伏笔猜测补齐；
- 是否只把身份事实作为定位和解释背景，没有直接升级为 `narrative_functions`。

身份记录只通过定位证据检查，不通过“身份看起来很像某种角色”来加分。

### 3.3 narrative function 有效性

每条 `narrative_functions` 都必须同时检查：

- `function_type` 是否有明确的 `actual_operation`；
- `target` 是否明确，能说明作用于谁、什么资源、什么信息或哪条局部剧情；
- 是否至少有一个实际行为、主动选择、资源流、信息流、冲突结果或关系变化证据；
- 是否说明了可观察后果，而不是只写“很重要”“推动剧情”“对主角有帮助”；
- `phase_scope` 和 `function_state` 是否与证据范围一致；
- 是否存在同一功能的重复或结构性证据，还是只有一次性行为；
- 是否把身份、性格、实力、出场频率或称谓当成唯一依据。

功能有效性按功能类型执行最低证据门槛：

| 功能 | 至少需要的有效证据 | 不足时的处理 |
| --- | --- | --- |
| `mentor` | 实际教学、纠错、训练、传授、示范或成长引导，并对主角行为/能力产生结果 | 只有年长、强大、老师身份时不得成立 |
| `validator` | 实际验证主角能力、身份、价值或资格的行为，以及验证后的结果或门槛变化 | 只有旁观、评价或同场时不得成立 |
| `resource_entry` | 持续、重复或结构化的资源通道，且资源真实经过人物或其权限流动 | 单次送物、口头承诺或偶然掉落只能记为事件 |
| `information_entry` | 实际改变主角的信息可得性、解释权、判断或行动 | 只有知道很多、身份神秘或说过一句话时不得成立 |
| `obstacle` | 反复或结构性阻断目标、资源、信息、选择或行动，并造成可见代价 | 只有立场敌对、口头挑衅或一次争执时不得成立 |
| `threat_generator` | 反复或结构性制造风险、约束、暴露、追杀、竞争或失败压力 | 只有实力强、名声大或属于敌方时不得成立 |
| `protector` | 有实际保护行为，并承担代价、暴露、资源消耗或改变主角风险 | 只有亲近、喜欢、年长或口头关心时不得成立 |
| `emotion_bearer` | 人物关系行为持续承载主角的确认、动摇、亏欠、压力或情感选择，并有剧情后果 | 不能用人物自身悲喜直接替代 reader emotion |
| `rival` | 有持续或重复的目标、资源、资格、评价或成长竞争，并影响双方选择或结果 | 一次比赛、争吵或实力接近时不得自动成立 |

其它功能必须按同一原则说明“实际做了什么、作用于谁、造成什么后果、证据在哪里”。

### 3.4 一人多功能与组合证据

检查 `function_combinations`：

- 同一人物是否可以同时承担多条已独立取证的功能；
- 每个成员功能是否都有独立证据，而不是多个标签共享一条身份描述；
- `combined_operation` 是否说明多个功能如何互相强化、冲突或在同一事件中共同生效；
- 是否把人物的职业、性格、实力和一个功能重复命名成“组合”；
- 只有一个功能时是否错误生成组合记录。

人物可以多功能，但“多标签”本身不是组合。没有联动条件和可见输出时，退回单功能记录或 `HOLD`。

### 3.5 relationship_function 与主角接口

逐条检查 `relationship_functions` 和 `protagonist_interface`：

- `relation_id`、双方人物和具体作用是否明确；
- `relational_operation` 是否描述人物在关系中实际施加、提供、阻断或验证了什么；
- `observable_change` 是否至少落到选择、资源、风险、信息、目标或关系反馈；
- `choices`、`resources`、`risks`、`cognition_information`、`goals` 和 `relationship_emotional_feedback` 是否分别表达不同影响，不以一段空泛评价代替全部接口；
- 主角是否真的因该人物改变了行动、资源使用、风险承担、认知、目标或关系选择；
- 是否把人物心情直接写成读者情绪结论；
- 是否把线路生命周期、世界制度、修炼成长或金手指机制复制进人物记录。

同框、亲近、讨厌、同队或血缘只能成为关系背景。若没有可观察作用，不能升级为关系功能或主角接口。

## 4. 第二层：功能与关系发动机有效性 QA

### 4.1 relationship_engines 的必要条件

每条 `relationship_engines` 必须回答：

1. 关系双方是谁；
2. `engine_type` 指向的利益、误解、竞争、保护、债务、秘密、身份差、共同目标或互补能力是什么；
3. `sustaining_condition` 为什么在后续仍然存在；
4. `recurring_plot_generation` 如何反复制造行动、选择、冲突、资源交换、信息变化、兑现或状态变化；
5. `observable_outputs` 在章节中实际出现了什么；
6. 是否有不止一次或具有结构性持续意义的证据。

以下内容不能单独成为关系发动机：

- 喜欢或讨厌；
- 亲属、同队、同学、上下级或恋爱称谓；
- 一次争吵、一次误会、一次救援、一次赠送或一次并肩作战；
- 角色经常同框但没有行动、资源、信息、风险或目标变化。

### 4.2 发动机持续性核验

检查关系发动机是否在不同章节或阶段重复生效：

- `sustaining_condition` 是否仍存在；
- 发动条件消失后，engine 是否已 `dormant` 或 `ended`，而不是无条件继续标记 `recurring`；
- 关系是否只靠重复同形冲突维持，没有新的选择、资源、信息、风险或兑现输出；
- 同一关系存在多个 engine 时，是否分别说明各自的持续条件和证据；
- 发动机是否真正改变了人物或主角的状态，而不是只改变情绪措辞。

如果发动机只有一次输出，保留为一次关系事件或 `UNKNOWN`；不得为了凑关系卡把一次事件升格为长期机制。

### 4.3 功能有效性与发动机的区别

人物功能回答“人物在故事里做什么”；关系发动机回答“这段关系为什么会继续产生剧情”。

- 人物可以是 `mentor`，但如果主角与其关系没有持续的资源、目标或价值条件，不自动生成关系发动机；
- 一段关系可以有 `competition` engine，但双方在具体场景中的人物功能仍需分别判断；
- `emotion_bearer` 描述人物关系对主角的剧情承载作用，不等于章节读者情绪母型；
- `resource_entry` 描述人物如何成为资源通道，不等于世界资源循环或修炼资源母型。

## 5. 第三层：功能转变与替代性 QA

### 5.1 function_transitions

每条 `function_transitions` 检查：

- `before_function` 在转变前确实已被证据支持；
- `trigger_event` 是可定位的事件、选择、冲突结果或关系变化；
- `after_function` 在触发后实际改变了人物对故事的作用；
- `evidence_refs` 至少覆盖触发前后，或覆盖足以证明变化的阶段节点；
- `protagonist_interface_change` 说明主角接口如何变化；
- 不是只因为态度改变、称呼改变、立场暂时一致或人物内心变化就宣称功能改变。

例如“敌对 → 合作”只有在人物从阻碍/威胁转为共同目标推动者、信息入口、资源入口或其它可观察功能时，才算 function transition。不能只写“后来关系变好了”。

旧功能的处理：

- 已被证据证明失效的旧功能不能无条件保留为当前功能；
- 仍间歇出现的旧功能可保留为多个阶段功能，但必须分开写 `phase_scope`；
- 功能来回切换且证据冲突时使用 `UNKNOWN` 或 `HOLD`，不强行压成单向成长线；
- 阶段变化必须属于人物功能专项，不把整卷结构或线路生命周期复制进来。

### 5.2 replaceability

检查 `replaceability` 是否有具体依据：

- `replaceable` 必须说明什么同类角色可以完成该功能、需要哪些条件；
- `identity_bound` 或 `non_replaceable` 必须指出绑定因素，如身份、秘密、资源、权力、血缘、历史债务、专属信息或独有关系；
- `reasoning` 必须引用剧情事实，不接受“核心”“重要”“作者重点写他”“实力最强”等空泛理由；
- 不能因为人物出场多、篇幅长、位置高或实力强就判断不可替代；
- 不确定时用 `UNKNOWN`，不要用主观重要性代替替代性分析。

替代性判断只针对“该功能是否能由其它人物完成”，不评价人物文学价值、读者喜爱度或作者偏好。

## 6. 人物功能重复与疲劳 QA

在单书 QA 中额外检查以下重复风险：

- 同类导师或验证者连续出现，但教学、验证和主角接口没有功能差异；
- 多个角色都只承担“送资源”，没有不同的资源条件、交换代价、权限或关系发动机；
- 关系长期只靠相同形式的争吵、误会或救援维持，没有新增选择、信息、资源、风险或兑现；
- 多个威胁制造者或反派只重复挑衅，没有新的约束方式、压力来源或主角接口；
- 新角色只更换身份、职业、阵营或外观标签，没有新增功能组合或关系发动机；
- 角色数量持续增加，但主角的选择、资源、风险、认知、目标或关系反馈没有发生变化；
- 同一人物在不同阶段重复使用同一功能标签，却没有新证据、新对象或新输出；
- 角色的“出场很多”掩盖了实际功能贡献低的问题。

疲劳 QA 不要求每个角色都必须独一无二，而是要求相似功能的差异能落到运行条件、证据、主角接口或关系发动机。无法区分时标记 `HOLD`、`insufficient_evidence` 或建议合并候选，不强行扩充角色功能数量。

## 7. 第四层：跨书 nearest-neighbor / clustering QA

### 7.1 跨书阶段门

只有同时满足以下条件，才允许生成 `nearest_neighbor` 或 `cluster`：

1. 所有目标书和冻结章节范围均已处理；
2. 每本书都有 `per_book` 或明确的 `gap`；
3. 每本书的单书 QA 已完成；
4. 关键人物功能、关系发动机和功能转变没有未标记的 `FAIL`；
5. 输入书籍和分片互不重叠；
6. 未用其它书的事实替代缺口书的证据；
7. cross-book completion gate 已明确通过。

任一目标书尚未完成时，只能保留单书候选、`gap` 或 `HOLD`，不得先行聚类。

### 7.2 nearest-neighbor 比较维度

近邻比较必须同时覆盖：

- `function_composition`：多个功能如何组合并产生可见剧情效果；
- `relationship_engines`：关系靠什么持续产生行动、冲突、选择、资源交换、信息变化或兑现；
- `function_transitions`：功能转变由什么事件或阶段触发，旧功能如何保留或失效；
- `replaceability`：功能为何可替代，或为何绑定特定身份、秘密、资源、权力、血缘或历史关系；
- `protagonist_interface`：人物如何改变主角的选择、资源、风险、认知、目标和关系反馈。

每条 `nearest_neighbor` 必须同时给出：

- 相似运行点；
- 关键差异和边界；
- 支撑相似与差异的 `evidence_refs`；
- `decision`：`merge_candidate`、`keep_distinct` 或 `insufficient_evidence`。

以下表面相似不能单独生成近邻：

`导师 / 妹妹 / 青梅 / 队友 / 反派 / 老师 / 上司 / 同学 / 恋人`

如果相同称谓背后的功能组合、关系发动机、转变条件或主角接口不同，必须 `keep_distinct`。

### 7.3 cluster 聚类规则

聚类必须从已通过单书 QA 的运行方式中提炼：

- `shared_operation`：共同的功能组合与关系发动机如何运行；
- `engine_pattern`：关系为什么能持续制造剧情；
- `transition_pattern`：功能何时、因何转变；
- `replaceability_boundary`：哪些条件可替代，哪些条件绑定特定人物；
- `protagonist_interface_pattern`：人物对主角状态造成的共同影响结构；
- `boundary_conditions`：与相近候选保持区分的条件。

允许以下结果：

- `unclustered`：证据不足或运行方式不能稳定归类；
- `insufficient_evidence`：只有表面相似，缺少关键行为或发动机证据；
- `HOLD`：存在边界争议、缺口或相邻专项职责冲突；
- candidate cluster：运行方式已能描述，但仍等待人工审核。

不强制凑簇。单书数量少、证据不足或只有共同称谓时，宁可保留 `unclustered`，也不生成空泛母型。

### 7.4 跨书置信度与状态

- 任一本书单书 QA 未通过，相关人物或书不能支撑 `HIGH` cluster；
- 任一关键比较维度是 `UNKNOWN`，只能使用 `MEDIUM` 或 `LOW`，并写明缺口；
- 所有 nearest-neighbor 与 cluster 仍然是 `candidate`；
- 不根据支持书数量自动升级为高频母型；
- 不把跨书相似结果写回正式人物库、素材库或总索引；
- 跨书比较只比较运行方式，不把人物专名、姓名、身份标签或题材皮肤写进聚类名称。

## 8. QA 记录与人工交接

QA 结果应回填 `schema.md` 规定的 `qa` 记录字段，不新增平行字段。至少保留：

- 输入范围、覆盖情况和来源冻结检查；
- identity/function 分离结果；
- 功能证据、组合证据和关系双方检查；
- relationship engine 的持续条件和重复输出检查；
- transition 的 before/trigger/after 证据链；
- replaceability 的替代条件或绑定因素；
- protagonist interface 的可观察后果；
- 相邻专项 interface/evidence 边界；
- 重复疲劳风险；
- 跨书阶段门、相似运行点、差异边界和 blocked outputs。

无法解决的判断交给 `handoff`：保留候选记录、关键证据、争议点、边界警告、缺口和建议动作。QA 不修改源章节，不修改人物正式资料，不升级状态，不写正式素材库。

## 9. 禁止将 QA 变成关键词规则

本文件提供的是人工和后续验证器可执行的判断边界，不允许仅凭关键词自动推断：

- 看见“老师”“强者”就判 `mentor`；
- 看见“给了资源”就判 `resource_entry`；
- 看见“告诉主角”就判 `information_entry`；
- 看见“保护”或“喜欢”就判 `protector`；
- 看见“争吵”或“敌对”就判 `relationship_engine`；
- 看见“后面合作”就判功能已转变；
- 看见“出场多”就判功能重要或不可替代；
- 看见相同人物称谓就判跨书相似。

后续 validator 只应检查可结构化的硬约束，例如字段存在、状态、证据引用、阶段门、`HIGH` 与关键 `UNKNOWN` 的冲突、before/trigger/after 是否完整等。复杂语义判断仍需证据审阅和人工 QA。

本文件只冻结人物功能专项的 QA、重复疲劳和跨书比较规则，不创建正式素材，不修改 schema，不提供人物事实，也不替代其它专项的业务判断。
