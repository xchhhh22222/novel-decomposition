# 输出协议

## WRITE

默认只输出可直接使用的对白场景，不展示内部分析。用户需要方案时，可先给两到三个明显不同的交流策略，再按选定策略成稿。

生成前确认或从上下文推断：人物、关系、场景地点、双方目的、必须释放的信息、必须抵达的结果、禁止改变的事实。缺少次要细节时做低风险处理；缺少决定剧情走向的关键信息时才询问。

正文要求：

- 开场尽快给人物一个正在做的事或现场压力；
- 重要人物各有目的，而非轮流配合主角；
- 新信息分散在选择、追问、误解和反应中；
- 动作密度随节奏变化；
- 结束时形成决定、关系、信息、风险或行动方向变化。

除非用户要求，不附“创作说明”。

## REWRITE

先锁定不可改变项：

- 事件顺序与结果；
- 谁知道什么；
- 角色立场与关系阶段；
- 战力、资源、伤势和位置；
- 已埋伏笔和必须保留的信息；
- 叙事视角、篇幅要求与文风边界。

只重写对白、紧邻动作、停顿、称呼和必要衔接。若原文存在事实矛盾，先标记，不能用改台词偷偷修掉。

默认交付：

1. 一句说明保留了哪些硬内容；
2. 完整可替换文本；
3. 仅在必要时列出未解决的事实问题。

用户要求“只给改稿”时省略第 1、3 项。

## AUDIT

不修改正文。先识别原场景的功能、冲突、有效爽点或情绪价值，再按影响分级：

- `必须修复`：信息越界、人物动机断裂、对白改变事实、严重失声纹、关系越界；
- `建议优化`：解释过量、标准问答、动作流水线、节奏均匀、潜台词不足；
- `可保留`：已经有效体现人物、关系、现场或推进的部分。

每个问题尽量包含：原句或准确位置、为何不成立、局部修法。引用只取识别问题所需的短句，不整段重复原文。

最后给结论：

- `PASS`：无明显问题；
- `PASS WITH TODO`：可用，有局部待修；
- `FAIL`：存在信息越界、关键动机错误、关系/事实冲突或大面积角色同声。

脚本命中只能进入“建议检查”，不能单独导致 `FAIL`。

## 组合请求

当用户要求“先检查再改”：先给简短审计结论，再给完整替换稿。不要边解释边打断正文。

当请求属于完整章节写作：服从负责章节事实、版本与写入权限的上层小说 Skill；本 Skill 只作为对白专项 Pass，不改变草稿/正式稿状态，也不自行写入文件。
