# 人物功能横向拆解器

## 模式路由

- 单书抽取：先读取 [schema.md](references/schema.md)。
- 横向近邻、聚类与 QA：再读取 [clustering-and-qa.md](references/clustering-and-qa.md)。
- 结构校验：运行 `python scripts/validate_outputs.py <jsonl或目录> --kind <per_book|nearest_neighbor|cluster|qa|handoff|gap>`；跨书必须额外提供 `--expected-books`、`--all-books-complete` 和 `--completion-manifest <per_book/gap.jsonl>`。

## 单一职责

本 Skill 不回答“这个人物是什么样的人”这一人物百科问题，而只回答：

> 这个人物在故事里承担什么功能、通过什么关系发动机持续制造剧情、这些功能何时发生变化？

核心对象固定为：

`人物功能组合 + 关系发动机 + 功能阶段变化`

有效的人物功能候选，必须能够回到章节或阶段证据，并说明人物如何通过实际行为、选择、资源流、信息流、冲突结果或关系变化，改变主角或故事的行动状态。姓名、身份、性格、职业、立绘、标签和简介只能作为定位信息，不能单独推出剧情功能。

本 Skill 不负责：

- 传统人物百科、人物小传、性格分析或单纯关系罗列；
- 主线、支线和线路生命周期；
- 分卷、阶段和篇章结构本身；
- 独立的剧情机制、事件套路或完整攻防链；
- 世界制度、组织规则和社会结构分析；
- 境界、技能、战力、资源成长或修炼体系；
- 金手指的输入、处理、输出、限制和成长循环；
- 章节读者情绪本身；
- 可直接入库的正式素材卡。

相关信息只能作为接口、依赖或证据引用，不能替代对应专项。

## 核心拆解层

执行时必须分别观察以下层，不得把它们压成一张传统人物卡：

### identity facts

只记录人物是谁、所属阵营、公开身份、已证实的特殊身份或与主角的定位关系，作为证据导航和功能解释的背景。身份事实本身不等于剧情功能。

### narrative functions

记录人物在故事运行中实际承担的功能，例如导师、竞争者、阻碍者、验证者、资源入口、信息入口、威胁制造者、保护者、情绪承载者。功能必须由可观察的行为和后果支撑，而不是由人物称谓或作者标签推定。

### relationship functions

记录人物与主角或其他关键人物之间，如何持续产生行动、冲突、选择、兑现、风险或状态变化。关系功能不是“他们关系很好/很差”的静态描述，而是关系在剧情中的发动作用。

### function combinations

同一人物可以同时承担多种功能，例如既是竞争者又是验证者，既是信息入口又是威胁制造者。禁止强制“一人一个标签”，也禁止因为一个显眼功能就抹去其它已证实功能。

### function transitions

追踪人物功能随章节或阶段的变化，例如：

`陌生竞争者 → 验证者 → 合作者`

每一次转变都必须有章节或阶段证据，至少能指出触发事件、行为变化、关系变化或主角接口变化。不能凭回顾性概括补造转变。

### replaceability

区分两类情况：

- 任何同类角色都能完成的通用功能；
- 依赖特定身份、秘密、资源、关系、能力或信息位置，因此难以由普通同类角色替代的功能。

替代性判断必须说明替代所需条件和证据；“很重要”“出场很多”不能直接证明不可替代。

### protagonist interface

说明人物如何改变主角的：

- choices：选择与行动方向；
- resources：资源获得、失去、交换或使用条件；
- risks：风险、限制、暴露和代价；
- cognition：认知、信息差和判断；
- goals：目标、优先级和推进路径；
- emotional feedback：由关系行为造成的情绪压力、确认、动摇或兑现反馈。

这里记录的是人物对主角接口产生的剧情效果，不把人物心情直接等同于读者情绪。

### relationship engines

关系发动机必须回答“为什么这段关系还能继续制造剧情”，并说明它如何产生行动、冲突、选择、兑现或状态变化。可观察的发动机包括利益、误解、竞争、保护、债务、秘密、身份差、共同目标、互补能力等，但这些词只是检索方向，不是无证据的自动标签。

喜欢或讨厌主角、一次争吵、一次帮助或一次同框，都不能自动构成稳定的关系发动机。

## 证据边界

证据优先级遵守上位总控契约：

1. 已通过 QA 的章节事实和行为证据；
2. 已确认的阶段、篇章或线路资料中与人物功能直接相关的证据；
3. 已存在且可核验的读者情绪覆盖，仅作为关系效果或兑现反馈的辅助接口；
4. BOOK DNA、人物索引和已有聚类，仅作定位和交叉核验；
5. 原文回查，只用于确认关键行为、资源流、信息流、冲突结果、关系变化、首次功能验证或章节归属。

书名、简介、题材标签、人物名字、人物称谓、立绘、宣传语和模型记忆不能独立支撑人物功能结论。证据不足时显式保留 `UNKNOWN`、`partial`、`gap` 或 `HOLD`，不根据常识补造人物功能、关系动机或阶段变化。

每条功能结论优先回到以下可观察证据：

- 人物采取了什么行为或主动选择；
- 人物改变了谁的选择、资源、信息、风险或目标；
- 资源或信息是否真实经过该人物流动；
- 冲突产生了什么结果，而不是只记录冲突存在；
- 关系是否因事件发生了可观察的变化；
- 主角是否因此改变行动、认知、目标、代价或情绪反馈；
- 该功能是否在后续章节继续产生剧情，而非只出现一次。

## 硬边界

以下判断不得自动成立：

- 人物性格 ≠ 剧情功能；温柔不自动等于保护者，严厉不自动等于导师；
- 人物职业、头衔或身份 ≠ 剧情功能；老师不自动等于导师，敌对阵营成员不自动等于威胁制造者；
- 喜欢或讨厌主角 ≠ 关系发动机；必须解释它怎样持续制造行动或选择；
- 出场多、同框多或叙述篇幅长 ≠ 功能重要；必须观察其造成的剧情变化；
- 实力强 ≠ 导师或威胁；战力只能作为功能证据的一部分；
- 帮助主角一次 ≠ 长期资源入口；要有重复、稳定或制度化的资源流证据；
- 和主角吵架一次 ≠ 有效冲突关系；要有持续的利益、目标、信息、身份、价值或资源矛盾；
- 角色触发某次外挂或金手指事件 ≠ 该人物就是金手指机制；
- 角色感到悲伤、喜欢或恐惧 ≠ 读者已经获得对应情绪；读者情绪由情绪专项负责。

不得从以下低证据来源直接推断功能：

`tags / portraits / names / titles / synopsis / genre labels / model memory`

## 与相邻专项的分工

- `novel-plotline-miner`：负责线路的起点、推进、转折、收束和生命周期；本 Skill 只记录人物如何推动、阻断、改向或验证线路，不重做线路。
- `novel-arc-structure-miner`：负责阶段、分卷、地图或结构节奏；本 Skill 只记录人物功能在这些阶段中的变化，不定义阶段结构。
- `novel-plot-mechanism-miner`：负责可复用的事件机制和因果链；本 Skill 只提供参与人物的功能与关系证据，不把人物关系直接升级成机制卡。
- `novel-worldbuilding-miner`：负责制度、组织、规则和社会结构；人物所属组织只作为身份背景或制度接口，不改写成人物 Skill 的制度分析。
- `novel-cultivation-system-miner`：负责成长、境界、技能、装备、战力和修炼循环；人物实力、资源和权限只作为功能证据，不生成修炼卡。
- `novel-golden-finger-miner`：负责金手指的输入、处理、输出、限制和成长；人物触发或参与一次外挂事件，不等于金手指机制。
- `novel-chapter-emotion-miner`：负责章节读者情绪、蓄压、兑现和余震；本 Skill 可以引用关系对读者情绪的影响作为辅助证据，但不能把人物情绪重新定义成 reader emotion。

如果一个结论同时需要其它专项才能成立，保留接口说明和证据引用，不越界代替其它专项完成结论。

## 上位契约与输入

严格遵守：

- `../../../SKILL.md`；
- `../../core/horizontal-specialist-contract.md`；
- `../../core/integration-and-qa.md`。

输入严格来自总控冻结的批次包。不得自行扩展书单、章节范围、来源、人物名单或输出范围，也不得用一本书的信息替另一本文本补齐人物功能。

输入至少应能说明目标书、允许章节或阶段范围、证据来源、已有情绪覆盖接口、已知缺口和禁止输出。缺少必要证据时停止升级结论，输出 `gap` 或 `HOLD`。

所有专项结果都必须使用共享的派生 envelope，并保持 candidate-only。具体字段、记录类型和 schema 已在当前 `references/schema.md` 与 `references/clustering-and-qa.md` 冻结；本文件不创建第二套 canonical schema。

## 运行流程

执行时按以下过程执行：

1. **冻结范围**：登记批次、目标书、章节/阶段范围、允许来源、已知缺口和禁止输出；
2. **定位人物与关系**：只从允许来源定位与主角、关键线路或当前阶段直接相关的人物和关系，不按简介扩展角色名单；
3. **提取行为证据**：记录实际行为、主动选择、资源流、信息流、冲突结果、关系变化和对主角接口的可见影响；
4. **分离身份与功能**：先标记 identity facts，再判断 narrative functions；不把职业、阵营、性格或称谓直接当作功能；
5. **判断功能组合**：允许一个人物同时承担多个已被证据支持的功能，并说明每个功能的独立证据与相互作用；
6. **判断关系发动机**：说明关系持续产生行动、选择、冲突、兑现或状态变化的原因；一次性互动只能记为局部事件，不能自动升级为稳定发动机；
7. **追踪功能变化**：按章节或阶段检查功能新增、减弱、替换、组合或转变，每次变化都绑定证据；
8. **检查替代性与主角接口**：判断功能是否依赖特定身份、秘密、资源或关系，并说明对主角选择、资源、风险、认知、目标和情绪反馈的影响；
9. **单书 QA**：检查证据覆盖、推断强度、重复记录、关系发动机是否有效、功能变化是否有证据、UNKNOWN/gap/HOLD 是否被保留；
10. **跨书比较**：只有所有目标书完成同类单书抽取和 QA 后，才生成 `nearest_neighbors` 与 `clusters`；比较功能组合和关系发动机的运行方式，不按导师、妹妹、队友、反派等表面名词直接聚类；
11. **人工交接**：输出候选、证据引用、相近候选、差异边界、阻断项和待确认决策，不自动入库。

支持多书批量处理时，各书和分片必须互不重叠；先独立完成单书结果，再在全批次完成后聚合。任何一本书证据不足，只标记该书的缺口，不用其它书的角色功能替它填空。

## 横向比较原则

跨书比较的对象是“功能如何组合、关系发动机如何运行、功能如何转变”，至少观察：

- 一个角色同时承担哪些功能，以及功能之间如何互相强化或冲突；
- 关系由什么利益、信息、身份、资源、目标或能力差异驱动；
- 关系发动机如何持续产生行动、阻碍、选择、兑现、风险或状态变化；
- 人物如何进入主角的资源、信息、风险、认知和目标接口；
- 功能变化由什么事件或阶段触发；
- 角色功能是否依赖特定身份、秘密、资源或关系，能否被其它角色替代；
- 功能组合和关系发动机造成了什么可见的线路推进、冲突升级或情绪反馈。

“都有导师”“都有妹妹”“都有队友”“都有反派”不能单独支撑近邻或聚类。表面身份可以作为检索索引，但必须降维到功能组合、关系发动机、证据链和阶段变化后再比较。证据不足时使用 `insufficient_evidence` 或 `HOLD`，不强行归类。

## 交付、状态与写入边界

默认输出位置（仅在用户授权后落盘）：

```text
素材库/DNA素材/05_人物功能与标签/per_book/
素材库/DNA素材/05_人物功能与标签/candidate/
素材库/DNA素材/05_人物功能与标签/qa/
```


每个专项批次固定规划五类交付：

1. `per_book`：单书人物功能、关系发动机、功能变化、替代性和主角接口证据包；
2. `nearest_neighbors`：按功能组合和关系发动机运行方式比较的近邻记录；
3. `clusters`：功能组合、关系发动机及其变体的聚类候选；
4. `qa`：证据覆盖、越界风险、推断争议、重复和阻断项；
5. `handoff`：交给人工审核的 candidate、证据引用、相近候选和待决策项。

必须遵守：

- 所有专项结果只能是 `candidate`；不得生成或升级为 `active`、`deprecated` 或正式素材卡；
- `UNKNOWN`、`partial`、`gap`、`HOLD` 和 `FAIL` 必须显式保留，并说明对下游比较的影响；
- 单书结果不能直接称为高频母型或稳定套路；
- `nearest_neighbors` 与 `clusters` 必须等待全部目标书完成单书抽取和 QA，并通过 cross-book completion gate；
- 不写正式素材库、总索引、章节事实、人物正式资料或其它正式产物；
- 不根据书名、简介或角色名字补造人物；
- 不修改相邻专项的 schema、索引、情绪记录或正式候选；
- 任何状态升级、正式入库、schema 变更或跨专项合并，都交给上位总控和人工审核。

## 禁止事项

- 把性格、职业、头衔、阵营、血缘或身份直接写成剧情功能；
- 把出场次数、同框次数、篇幅或作者称谓当作功能重要性的证明；
- 因为实力强、年长、年幼或地位高就自动标记导师、保护者或威胁；
- 因为一次帮助、一次争吵、一次资源赠予或一次信息透露就建立长期关系发动机；
- 从人物标签、立绘、名字、简介、宣传语或模型常识反推功能；
- 把人物情绪直接当成读者情绪结论；
- 把角色参与金手指、修炼、制度或剧情机制的事实改写成对应专项的完整结论；
- 在所有目标书完成前建立跨书近邻或聚类；
- 把单书候选写成 `active`、`deprecated` 或正式素材卡；
- 为了填满人物功能或关系链而补造行为、动机、资源、信息、冲突结果或阶段转变证据。

## 交付前验收

每次交付前至少确认：

1. identity facts 与 narrative functions 明确分离；
2. 一个角色可以承担多种功能，不被强制压成单标签；
3. 每条功能结论都能回到行为、选择、资源流、信息流、冲突结果或关系变化证据；
4. 每个 function transition 都有章节或阶段证据；
5. relationship engine 能解释持续产生行动、冲突、选择、兑现或状态变化，而非只记录态度或一次互动；
6. replaceability 明确区分通用功能与绑定特定身份/秘密/资源/关系的功能；
7. protagonist interface 覆盖 choices、resources、risks、cognition、goals 和 emotional feedback；
8. 与 plotline、arc-structure、plot-mechanism、worldbuilding、cultivation、golden-finger、chapter-emotion 的边界没有职责泄漏；
9. 五类交付、derived envelope、candidate-only、UNKNOWN/gap/HOLD 和 cross-book completion gate 均由当前 schema、validator 与交付流程承接；
10. 没有写入正式素材库、总索引或其它正式资料的路径；
11. 跨书比较基于功能组合与关系发动机的运行方式，而不是表面角色名词；
12. 本文件不偷偷形成完整 schema，不替后续 schema 文件预先冻结字段表。

本文件冻结人物功能专项的职责、证据边界、相邻分工、输入输出原则和运行流程；具体记录字段、聚类结构、QA 规则和验证脚本以当前 references 与 scripts 为准。
