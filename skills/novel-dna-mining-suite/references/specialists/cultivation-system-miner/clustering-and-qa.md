# 修炼成长系统聚类与 QA 规则

本文件只规定 `novel-cultivation-system-miner` 的派生审核、成长一致性和跨书比较方法。正式字段以同目录 `schema.md` 为准；本文件不新增 schema 字段，不修改源章节、正式卡或正式素材库。

## 一、审核顺序与硬边界

按以下顺序审核：

1. 输入书籍、章节、来源和情绪覆盖是否冻结且可追溯；
2. 单书八层记录是否有证据或显式未知；
3. 境界、技能、战力、资源、权限之间是否发生串层；
4. 成长状态是否前后一致，节奏是否出现成长替代或验证疲劳；
5. 所有单书 QA 完成后，再进行 nearest-neighbor 与 clustering；
6. 最后检查 handoff 是否保留候选边界和待确认项。

任何一层失败都不能靠下一层的聚类、战果或更强措辞覆盖。所有结果保持 `candidate`；`active`、`deprecated` 和正式入库不属于本专项输出。

## 二、单书修炼体系 QA

### 2.1 范围、证据与覆盖

- 检查目标书、章节范围、允许来源、情绪 overlay 和提取版本是否与总控冻结包一致。
- `per_book` 的八层记录必须能沿 `evidence_refs` 回到章节、阶段或已通过 QA 的 overlay；不能只写“原文设定”“前期如此”等不可定位描述。
- 每一层可以是 `partial` 或 `UNKNOWN`，但缺口必须进入 `unknowns` 或形成 `gap`，不能用另一层的事实补齐。
- `per_book` 与 `gap` 对同一本目标书不能并存；若证据不足，应保留一条结构清楚的 `gap`。
- 书名、简介、题材、宣传语和模型常识不能独立支撑境界、突破条件、技能状态或战力判断。
- `HIGH` 不能带关键 `unknowns`；章节事实 QA 为 FAIL 或关键层无法核验时，不支持高置信下游聚合。

### 2.2 通用体系与主角特例

`universal_system` 中的规则必须有证据说明其适用于所有或大多数修炼者，或至少被公共制度、教师、组织、检测体系或多个角色共同验证。

以下情况不能直接写成公共规则：

- 只有主角能使用的外挂功能；
- 只有主角拥有的天赋、体质、技能组合或资源通道；
- 只发生在一次特殊场景中的临时规则优势；
- 只由角色口述、没有公共验证或行动后果的传闻。

主角特例应放入 `protagonist_build`、`golden_finger_interfaces`、`actual_combat_power` 或对应 `UNKNOWN`，并保留证据边界。

### 2.3 境界直接证据

每个 `transition_events` 都要按下列链检查：

`before → trigger_or_condition → after → change_type → direct_evidence_refs`

- `before` 和 `after` 必须指向正式境界或明确的 `UNKNOWN`；
- `trigger_or_condition` 要说明突破条件、训练完成、检测确认或体系认可的变化；
- `change_type=formal_realm_change` 必须有直接证据；
- 不能因为“突破”“变强”“击杀强敌”“越级胜利”“获得称号”“装备到手”就自动补出新的 `after`；
- 缺少直接境界证据时，不能填写确定突破，必须降为 `UNKNOWN`、`partial`、`HOLD` 或 `gap`；
- 同一次事件不能同时被无证据地重复记为境界提升、技能提升、实际战力提升和永久资源转化。

### 2.4 八层职责检查

逐条确认：

- `universal_system` 记录公共成长规则，不记录主角独有特例；
- `realm_system` 记录阶段与突破，不记录单次战斗结果；
- `protagonist_build` 记录主角选择、组合和取舍，不替代人物功能或主线动机；
- `golden_finger_interfaces` 只记录外挂怎样影响成长，不重拆输入/处理/输出；
- `actual_combat_power` 记录名义境界、观察表现和修正来源，不反向推境界；
- `skill_proficiency` 记录技能状态变化，不把技能获得自动写成掌握或精通；
- `equipment_resources` 记录物品、消耗和转化，不把资源到账自动写成永久成长；
- `identity_permissions` 记录训练、资源、地图和信息入口，不把权限自动写成修炼等级。

若一个结论同时属于两个层次，应保留接口或 evidence reference，而不是复制成两个独立的正式结论。

## 三、防串层 QA

### 3.1 战果与境界

- 击杀强敌不能自动证明 `realm_system.transition_events`；
- 越级表现不能反推名义境界；
- 胜负、逃脱、任务完成和旁观者震惊只能进入 `actual_combat_power.combat_result` 或其证据；
- 若 `realm_change_proven=false`，不得同时声称人物已经进入确定的新境界；
- 短时爆发、规则克制、环境优势、阵地、战术和信息差必须作为 `modifiers` 或接口保存。

### 3.2 技能状态

技能状态必须区分：

`obtained → learning/practiced → mastered → proficient → evolved`

这不是强制线性升级，而是证据状态。检查：

- 获得技能不等于学习完成；
- 学习或练习不等于稳定掌握；
- 单次成功施展不等于 `mastered` 或 `proficient`；
- `mastered`、`proficient`、`evolved` 必须有相应 `visible_validation`；
- 技能熟练度提升不能自动进入 `realm_system.transition_events`；
- `obtained` 直接跳到 `mastered/proficient/evolved` 时，必须能指出学习、训练、实战、失败修正或体系确认的证据；否则降级或 HOLD。

### 3.3 装备、资源与自身成长

- `temporary_boost`、药效、装备加成、外部辅助、环境和阵法不能直接写成自身基础战力永久提升；
- `consumable` 必须说明消耗或失效边界；
- `long_term_conversion` 必须说明资源如何被训练、吸收或转化；
- `permanent_self_growth` 必须有直接证据说明自身基础状态持续改变；
- `access_only` 只能说明入口、资格或机会，不能写成境界或永久战力；
- `permanent_self_change_proven=false` 时，不得在其它层把该资源使用记录成永久成长；
- 装备已消耗、失效或离身后，后续记录不能继续把它当作常驻增益；若原文前后冲突，标记冲突或 HOLD，不自行解释。

### 3.4 身份、权限与成长路径

- 权限可以打开训练、资源、地图或信息入口，但不等于修炼等级提升；
- `growth_effect_type=access_only` 不能被当成 `formal_growth`；
- 只有存在直接证据时，权限才可改变突破条件或正式成长状态；
- 军衔、学生资格、组织职位、秘境准入和资源领取资格不能自动进入 `realm_system`；
- 权限变化若只是改变“能不能进入”，应留在 `identity_permissions`，不要写成实际战力增长。

### 3.5 金手指、世界观与主线接口

- 金手指提供资源、效率、选择权或结果时，区分外挂造成的接口影响与修炼体系本身规则；
- 社会如何分配资源、谁垄断资源和制度如何运作属于 worldbuilding；本专项只记录资源如何进入修炼成长；
- “为什么必须升级”属于 plotline；本专项只记录系统如何允许或要求成长，不补写主线动机；
- 任何接口都必须有引用和边界，不能复制相邻专项的正式业务字段。

## 四、成长状态一致性与节奏 QA

以下是派生判断，不新增 schema 字段。可利用 `transition_events`、`actual_combat_power`、`skill_proficiency`、`equipment_resources`、`identity_permissions`、`milestones`、`unknowns` 和 `evidence_refs` 记录结论。

### 4.1 状态一致性

- 名义境界与实际战力可以不一致，但 `power_gap_explanations` 必须指出修正来源；
- `realm_change_proven=false` 时，不能出现确定的新境界状态；
- `permanent_self_change_proven=false` 时，不能把资源使用写成永久成长；
- 技能若从 `obtained` 跳到 `mastered/proficient/evolved`，必须有对应验证；
- 同一人物的境界、技能状态、装备归属和资源状态若前后冲突，应标记冲突、UNKNOWN 或 HOLD；
- 不能把装备已消耗、权限已撤销或 buff 已结束后的效果继续算作当前固定能力；
- 任何“补回前后逻辑”的解释都必须有证据，不能靠网文常识自动修正。

### 4.2 成长揭示与验证节奏

检查是否出现：

- 首次通用体系展示；
- 首次境界展示；
- 首次直接突破或正式境界变化；
- 首次技能掌握验证；
- 首次实际战力验证；
- 连续多章只有资源到账，没有训练、转化或能力验证；
- 连续多次“突破”但阶段差异不可见；
- 境界提升过快但训练、条件、代价或直接证据缺失；
- 技能大量获得但缺乏学习、使用和掌握验证；
- 装备与资源长期替代主角自身成长；
- 权限不断提升，但成长系统没有实际变化。

这些是风险判断，不是强行补奖励的理由。优先建议验证既有规则、补充证据或标记缺口，不得为了消除节奏风险新增境界、技能或永久资源。

## 五、跨书 nearest-neighbor QA

只有全部目标书完成单书抽取和 QA 后才允许比较。nearest-neighbor 必须同时写出相似运行点、关键差异、证据和未知项。

至少比较：

- 公共成长循环如何运行；
- 境界突破需要什么条件，如何被直接确认；
- 主角如何构筑并承担取舍；
- 实际战力如何与名义境界脱钩；
- 技能如何从获得走向学习、掌握、精通和演化；
- 资源如何转化为成长，以及临时/消耗/长期转化的差异；
- 权限如何打开训练、资源和地图路径；
- 金手指如何接入但不替代公共体系。

以下表面共现不能单独建立近邻：

- 都有“一境二境”；
- 都有炼体炼气；
- 都有技能树或技能升级；
- 都有丹药、装备、突破或越级战斗。

若公共成长循环、突破条件、技能状态验证或资源转化方式不同，即使名词相同，也应 `keep_distinct` 或 `insufficient_evidence`。

## 六、跨书 clustering QA

聚类单位是可复用的成长运行方式，不是等级名称、战果、丹药名或题材皮肤。聚类前确认：

- 每本书都完成单书抽取和 QA，或明确标记 QA 缺陷；
- 共同机制至少有公共规则、成长条件、状态变化或验证中的可比证据；
- 组内相似性来自运行方式，不是同名异义；
- 阶段、战力、技能、资源和权限差异没有被一个宽泛标签抹平；
- 每个簇都有成员证据、边界条件、反例或未决项。

允许：

- `unclustered`：有成长记录，但无法与其它书形成可靠共同运行结构；
- `insufficient_evidence`：表面相似，但证据不足以确认同类系统；
- `HOLD`：存在直接证据冲突或高影响未知，暂缓归簇。

QA 未通过的书不能支撑 `HIGH` cluster。不得为满足数量、覆盖率或完整度强行归簇；cluster 只能是 `candidate`，不写正式素材库。

## 七、回收与交接检查

### 7.1 `qa`

QA 至少回答：

- 哪些公共规则有跨角色证据；
- 哪些境界变化有直接证据；
- 哪些技能状态只是获得或学习，哪些已被掌握验证；
- 哪些战果只是实际战力表现；
- 哪些资源是临时、消耗、长期转化或永久成长；
- 哪些权限只打开入口；
- 是否发生境界、战力、技能、资源、权限串层；
- 是否存在 UNKNOWN、gap、冲突、节奏疲劳或跨书阻断。

### 7.2 `handoff`

handoff 只传递候选成长机制、证据、差异、未知项、待核验问题和适用边界。不得把“战力强”“升级快”“技能多”直接改写成母型名，不得授予正式入库权限。

### 7.3 完成判定

专项只有在以下条件同时满足时才可标记完成：

- 五类交付均有记录或明确空结果说明；
- 八层职责均有承载位置，且不存在未解释的串层；
- 正式境界变化都有直接证据链；
- 技能状态、实际战力、资源效果和权限入口可分别追溯；
- `partial`、`UNKNOWN`、`gap`、`HOLD` 没有被伪装成完整结论；
- 单书 QA 完成前没有正常跨书比较；
- 没有越界替代金手指、世界观、人物、主线、开篇、篇章或剧情机制专项；
- 没有写入正式素材库或本书正式设定。
